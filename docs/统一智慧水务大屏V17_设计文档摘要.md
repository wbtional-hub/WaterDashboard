# 统一智慧水务大屏 V17 设计文档摘要

- 主设计文档：`统一智慧水务大屏V17_AI开发记忆体与CODEX工程治理增强版设计文件_中文版.docx`

- 文档封面副标题仍显示 V14，这是历史累计文档中的遗留标识，不影响 V17 章节作为当前最新治理依据。

## 系统定位

本项目是“统一智慧水务大屏系统”，定位为独立部署、独立启动、独立运行的智慧水务大屏微服务产品。系统不与任何既有水务业务系统绑定启动，通过配置数据源、SQL、API、GIS 服务、三维资源、组件模板和发布版本，对接任意水务系统。

平台目标不是交付一套写死数据和页面的静态大屏，而是形成可拖拽、可配置、可保存、可预览、可发布、可回滚、可诊断的产品化大屏平台。

## 固定技术栈

| 能力 | 固定技术路线 |
| --- | --- |
| 平台数据库 | PostgreSQL |
| 空间数据库 | PostgreSQL + PostGIS |
| 二维 GIS | OpenLayers |
| 三维组件 | Babylon.js |
| 普通图表 | Apache ECharts |
| 关系拓扑、调度链路、AI 证据链 | @antv/g6 |
| 图标与轻量动效 | SVG / Iconfont / CSS / Lottie |
| AI 模型调用 | AI Gateway |

各渲染引擎按专业职责分层协同，不得将某一种引擎扩张为所有场景的统一替代方案。

## 数据源配置与卡片数据闭环

- 数据源配置中心统一管理关系数据库、API、GIS 服务、实时数据、三维资源等接入能力。
- 平台自身配置库固定使用 PostgreSQL；外部业务数据库按客户现状通过只读方式接入，不强制改造为平台数据库。
- 数据源应支持分组、连接测试、环境隔离、权限控制、脱敏配置、健康检查和审计。
- 卡片通过选择数据源、填写 SQL 或 API、预览结果、配置字段映射、样式和刷新策略完成数据绑定。
- 卡片 SQL 只允许 `SELECT`，必须具备解析、参数化、限行、超时、审计和脱敏诊断能力。
- 禁止执行 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`TRUNCATE`、`CREATE`、`GRANT`、`REVOKE` 等写入或高风险语句。
- 数据库密码、Token、连接串、密钥等敏感信息不得返回前端。

## 组件配置与发布模型

- 组件模板定义可复用的视觉、数据契约、字段映射规则、默认样式和运行时能力。
- 组件实例保存大屏中的位置、尺寸、数据绑定、字段映射、样式、刷新、权限和 AI 配置。
- 所有卡片配置必须可序列化、可保存、可发布、可回滚。
- 编辑态、预览态、发布态、浏览态必须分离；保存草稿不能影响已发布浏览页。
- 发布前执行体检，覆盖数据源、SQL、字段映射、空数据、超时、AI 上下文、地图图层和性能风险。
- 发布后生成不可变版本快照，浏览页只加载已发布版本。
- 单个卡片异常只能影响当前卡片，不能导致整张大屏白屏或停止运行。

## GIS 与三维能力

- OpenLayers 是二维 GIS 主入口，负责底图、图层、要素、空间查询、对象点击和卡片联动。
- PostgreSQL + PostGIS 保存水务对象、点线面图层、空间索引和空间分析结果。
- Babylon.js 用于厂站、泵房、设备、管廊、三维告警、对象拾取和状态联动。
- GIS、三维资源和业务卡片之间应通过统一对象编码建立联动关系。

## AI 辅助与边界

- AI 是上下文感知的辅助能力，不是大屏主体，也不能替代人工决策。
- AI 模型调用必须统一通过 AI Gateway，不允许前端或普通业务接口直连模型。
- AI 只能分析当前已发布、已拖入、已启用 AI、当前用户有权限，并且进入 Dashboard Context Manifest 的卡片。
- AI 不得读取未拖入大屏的看板、未发布草稿、未启用 AI 的卡片、无权限字段或未经脱敏的数据。
- AI 输出应包含摘要、依据、风险、建议、置信度和引用卡片，形成可解释的证据链。

## 权限控制

- 权限模型采用 RBAC + ABAC + 资源实例权限的组合方式。
- 权限控制必须覆盖大屏、卡片、数据源、SQL、GIS 图层、三维资源、组件模板、AI 上下文、日志诊断等资源。
- 大屏设计、预览、发布、回滚、浏览、导出和诊断等操作必须按权限控制。
- 普通用户只看到友好错误提示；管理员和运维诊断人员只能查看脱敏诊断信息。

## 知识产权保护与产品授权

- 必须设计知识产权保护、软件授权、防盗版、防二次销售机制。
- License Center 应支持在线激活、离线激活、客户与项目绑定、环境与节点限制、功能授权、到期提醒和授权审计。
- License 文件、组件包、主题包、地图样式包、三维资源包应支持非对称签名、校验和与完整性校验。
- 组件模板应包含组件编码、版本、发布者、签名、校验和和授权范围等元数据。
- 图标、Lottie、三维模型、地图样式和主题包等资产应具备资产 ID、版本、资产水印和溯源能力。

## 日志、诊断与可追溯

- 所有异常必须可追踪，并通过 `traceId` 贯穿前端、后端、数据源查询、GIS、三维和 AI Gateway。
- 配置变更、发布、回滚、SQL 执行、AI 调用、权限拒绝、License 校验和错误诊断必须记录日志。
- 单个卡片错误、慢查询、接口超时、地图图层失败、三维资源失败和 AI 不可用均应独立降级。
- 普通用户不得看到 SQL、密码、Token、连接串、密钥、堆栈等敏感信息。
- 管理员可通过脱敏的错误摘要、卡片标识、数据源标识、SQL 摘要、耗时、错误码和 `traceId` 定位问题。

## CODEX 开发治理

- 仓库根目录必须维护 `AGENTS.md`、`AI_MEMORY.md`、`AI_DEVELOPMENT_RULES.md`、`CODEX_TASK_LOG.md`、`CODEX_NEXT_TASK.md`。
- 每次开发前必须读取上述记忆体文件和 `docs/` 目录下最新 V17 设计文档或摘要。
- 每次开发前必须输出当前理解、任务范围、不会修改的范围、风险点、预计新增或修改文件清单。
- 未完成开发前检查，不允许直接修改代码。
- 每次开发完成后必须更新 `CODEX_TASK_LOG.md` 和 `CODEX_NEXT_TASK.md`。
- 开发应优先完成最小闭环，再逐步增强；不得一次性开发完整系统，不得破坏已完成的正常功能。

## 第一阶段最小闭环方向

第一阶段应围绕独立系统启动、PostgreSQL 平台配置库、数据源配置中心、组件模板管理、大屏编辑器、卡片 SQL 配置、字段映射、草稿保存、预览体检、版本发布和浏览页加载形成可运行闭环，并预留 Dashboard Context Manifest、单卡片错误隔离、脱敏诊断和 `traceId`。
